Note on terminology: "Dynamic Memory Clock" is ASRocks BIOS-UI name for the underlying Intel **System Agent Geyserville (SAGV)** mechanism. Other vendors UI-rename the same mechanism: ASUS = "Adaptive Memory Boost", MSI = "Memory Try It! / Dynamic Memory Boost", Gigabyte = "Memory Power Down / Dynamic Memory Profile". The live workpoint signal we read from `MCHBAR + 0x5C` is the SA-Geyserville state machine itself, regardless of what the BIOS calls it. A separate "SAGV" toggle in some BIOSes may control SA *Voltage* Geyserville (voltage-side scaling) and is distinct from the frequency-side toggle.

### Decoded sample 1 (gear-aware formula)

- QCLK       = ratio x ref = 117 x 33.333 MHz = **3,900.000 MHz**
- Data rate  = QCLK x gear = QCLK x 2 = **7,800 MT/s** (DDR5-7800)
- IO clock   = data_rate / 2 = QCLK x gear / 2 = **3,900 MHz**  (= HWiNFO/CPU-Z "Memory Clock")

Note: `data_rate = QCLK * gear` is the gear-aware general form. The PTL script hardcodes `QCLK * 2 * 2`, which is correct only for Gear4 -- on Gear2 hardware (typical Arrow Lake) it overestimates by 2x and reports a non-existent DDR5 speed grade.

## Live IOCTL -- `ioctl_read_imc_clock_live` (workpoint)
On Arrow Lake-S the inherited PTL/MTL/LNL live source `SA_PERF_STATUS` at `MCHBAR+0x5918` reads as `0x00000000` regardless of SAGV state, so a different register had to be located. A passive 5-minute MCHBAR scan (`Deploy/Detect-ARLLiveIMC.ps1`) followed by an autonomous load-correlation pass (`Deploy/Verify-ARLLoadCorrelation.ps1`) and a cross-BIOS validation across DDR5-7800 and DDR5-7000 identified the live workpoint at `MCHBAR + 0xE448` (`IMC_LIVE_GV_STATUS_ARL`). Encoding mirrors the SA_PERF helper but takes bits 7:0 (instead of bits 9:2) as the live QCLK ratio against BCLK/3.

Cross-BIOS validation (raw register values, before clamp):

| BIOS DRAM speed | Trained max (MEMSS_PMA) | Low raw | Low ratio | High raw | High ratio raw | High ratio after clamp |
|---|---|---|---|---|---|---|
| DDR5-7800 (this run) | 117 | `0x04B00048` | 72 | `0x079F0076` | 118 (=trained_max+1) | **117** |
| DDR5-7000 (cross-check) | 105 | `0x04B00048` | 72 | `0x06D7006A` | 106 (=trained_max+1) | **105** |

Two findings worth highlighting:

1. **The low-state ratio is 72 on both BIOS-trained DRAM speeds, regardless of trained max.** The SAGV floor on ARL is a firmware-fixed property equivalent to `DDR5-4800` (= JEDEC base spec), not a fraction of trained max as on some older Intel parts.
2. **The raw high-state ratio is consistently `trained_max + 1` across both BIOS configs.** This 33-MHz "PLL overshoot" / encoding tolerance is a known property of this register. The IOCTL clamps `ratio > trained_max` down to MEMSS_PMA's trained max so output matches what HWiNFO and CPU-Z display (both of which read this value through Intel PMT/CTL, which applies the same clamp internally â€” see `cpuz.exe` RE notes in `PR_discussion.md`). The `Raw` column in the live samples table below preserves the un-clamped register dword for forensics; the `Ratio` column shows the post-clamp value the consumer sees.

Mirrored at `MCHBAR + 0xEC48 / 0xF448 / 0x1E448 / 0x1EC48 / 0x1F448` (per-channel replicates). Under sustained 30 GB/s memcpy load every poll returns the high state (3658/3658 = 100%); in idle ~88-91% high and dips to the low state ~9-12% on memory-burst activity. With Dynamic Memory Clock enabled and OS power profile = Balanced, the low workpoint is hit much more frequently. See `Deploy/VERIFY-ARL-LoadCorrelation.md` for the full distribution.

Active during this run: Dynamic Memory Clock = **enabled**, SAGV BIOS toggle = not explicitly set (default). The bimodal swing only occurs while a frequency-scaling mechanism is active; with Dynamic Memory Clock disabled the register is expected to sit permanently at the high state (not yet verified on this hardware).

## Cross-validation against external references

External cross-check via HWiNFO64 v8.32 -- see [`screenshots/ARL_hwinfo_memory_clocks.png`](../screenshots/ARL_hwinfo_memory_clocks.png) for the captured Sensors view.

| Source                                    | Reported value                            | Notes |
|---|---|---|
| Module static IOCTL                       | 3,900 MHz IO clock (7,800 MT/s)           | derived as `QCLK x gear` (Gear2) |
| HWiNFO64 Memory Clock                     | 3,899.6 / 3,899.8 / 3,900.6 MHz (min/cur/max) | matches module IO clock to within sub-MHz jitter |
| HWiNFO64 Memory Clock Ratio               | 39.00x                                    | 39 = 117 / 3 (HWiNFO ratio is vs BCLK; module ratio is vs BCLK/3) |
| HWiNFO64 Gear Mode                        | 2                                         | matches module's `Gear2` decode |
| Win32_PhysicalMemory.ConfiguredClockSpeed | 7,800 MT/s (per DIMM)                     | matches module data rate |
| EXPO kit name `G.Skill F5-7800J3646H16G`  | DDR5-7800 nominal                         | matches module data rate |

Four independent references -- the module's own `MCHBAR_MEMSS_PMA` decode, HWiNFO64's Memory Clock sensor (incl. matching Gear Mode), the SMBIOS DRAM data the firmware publishes, and the EXPO kit's nominal speed grade -- all agree on **DDR5-7800, IO clock 3,900 MHz, Gear2**. The gear-aware formula `data_rate = QCLK * gear` reproduces this exactly; the legacy `QCLK * 2 * 2` shortcut from `Test-IntelIMC.ps1` would have predicted DDR5-15600 and disagreed with every reference, confirming that path is incorrect for non-Gear4 hardware.

Based on this four-way agreement, `is_platform_validated` in `IntelIMC.p` was extended to include `PLAT_ARL` alongside `PLAT_PTL`. The static IOCTL therefore no longer sets the `EXPERIMENTAL` bit on Arrow Lake -- the `Flags` column above reads `0x1` (`STATIC_LOCKED`) instead of the previous `0x5` (`STATIC_LOCKED | EXPERIMENTAL`). Consumers can expose the sensor as a primary value on ARL without the preview/experimental label.

## Reproducibility

```powershell
# from an elevated PowerShell at the repo root, with the unrestricted
# PawnIO driver loaded and IntelIMC.signed.amx present:
.\Deploy\Build-ARLValidation.ps1
```

The static MEMSS_PMA line is locked at MRC and does not change at runtime; re-running on the same machine MUST produce identical static values. The live IOCTL samples a SAGV state machine, so the per-sample distribution will vary slightly run-to-run depending on background memory activity; the SET of distinct ratios should remain {70, 117} (or a documented superset if more workpoints get exposed under different load profiles).
